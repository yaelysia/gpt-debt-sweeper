# 删除决策与证据规则

目的：为 Phase 2 提供**维护价值与契约证据**的判断方法，而不是重做 Phase 1 或仅统计死代码。

## 维护价值判断：被调用的代码也可能多余

在 Phase 2 对每个**技术债簇**提出一个实际问题：**继续维护这套职责/状态/接口，当前产品究竟获得了什么价值？**

例如 `有效业务入口 → LegacyAdapter → Forwarder → 当前实现`。即使每一层都有调用者，若两个中间层只原样转发，且不承载协议转换、权限隔离、资源所有权、稳定对外接口或真实兼容义务，就应把有效调用者直接接至当前实现，然后整组删除两层及其专属测试/配置。

判断优先级：
1. 是否存在**必须保留的独立行为或契约**？存在则保留行为，必要时只收敛其冗余实现。
2. 是否只增加另一条执行路径、真相源或配套维护工作，而有效消费者可以直接复用现行实现？若证据明确，倾向清理。
3. 清理后是否真的减少独立维护概念，还是只是转移复杂度并新增胶水代码？后一种不做。

这不是以主观“感觉没价值”替代证据。若涉及受支持的行为、外部消费者或历史持久化承诺，必须有对应依据；不确定时对该项继续定向调查或跳过。

## 一、先确定要删除的“概念”，不是先删单个文件

对候选用一句话表达：

- 当前还承担什么职责？
- 是哪个实际生产入口、外部用户、持久化数据或已支持协议需要它？
- 如果整个概念消失，现行行为会失去什么？
- 它关联的代码、配置、测试、发布产物和文档有哪些？

一个候选可能包含多个模块，多个文件也可能只构成一项过期概念。

## 二、消费者证据的优先级

1. **有效业务/外部契约**：真实用户能力、公开 API、受支持协议、安全与授权要求、历史持久化数据、运行平台。存在时必须保留或先按用户已授权的产品决策迁移。
2. **实际生产可达性**：入口、路由、调用者、事件/队列、动态导入、DI、插件注册、构建/打包、运维脚本、外部包使用。需要读取上下游，不以引用次数代替理解。
3. **独立验证依据**：与具体用户可观察结果或现行规范对应的测试、独立 Oracle、已复现的回归场景。可成为保留证据，但要辨别它保护的是有效契约还是已退役内部行为。
4. **弱证据**：同族旧代码、Mock、Fixture、注释、历史文档、仅为目标存在而生成的测试。它们会提示继续调查，单独不足以证明目标仍必须保留。

搜索时覆盖：符号名、文件名、目录、大小写/别名、import 路径、序列化字段、事件/协议字符串、命令行入口、环境变量、生成代码模板及外部调用线索。需要时查看 Git 历史和当前迁移说明。

**生产路径无引用 ≠ 可立即删除；存在真实调用 ≠ 中间结构必要；测试引用存在 ≠ 永远必须保留。**

## 三、三种裁决

**DELETE / COLLAPSE**
- 已确认现行行为由另一条路径承担，或该行为已经正式退役；
- 已检查与该目标有关的动态入口、配置、外部/持久化契约，未发现有效保留理由；
- 可完整收尾关联产物，或能将有效调用者直接迁到剩余的唯一实现。

**KEEP**
- 仍有真实生产消费者，或属于受支持的可观察行为；
- 有实际信任、故障隔离、协议兼容、资源生命周期或独立验证需要；
- 删除只是把复杂度搬到另一层，未减少需维护的概念。

**INVESTIGATE / SKIP**
- 动态引用、外部消费者或旧数据依赖尚有实质疑点；
- 没有足够信息判断其行为是否已退役；
- 清理需要决定取消仍支持的产品能力，而用户未作此授权。

对能解决的疑点继续定向调查；难以证实则跳过该候选，继续处理同范围的其他工作。不以无穷穷举追求绝对确定。

## 四、识别“互相证明存在”的冗余簇

示例：多余内部校验 → 专属测试 → 专属 Fixture → 为 Fixture 增加的新参数。

逐层追问是否存在**不依赖这一簇自身**的当前需求、真实调用者、独立 Oracle 或故障边界。只有彼此引用而没有独立依据时，优先移除整簇。

特别区分：
- 生产者和验证者拥有相同数据与算法时，重新计算不一定产生独立的验证价值。
- 即使某条测试是目前唯一的可执行规格，只要它保护的确实是仍支持的独立外部行为，就不能以“循环证明”为借口删除。
- “断言旧字符串不存在”的测试常是冗余；但防止敏感信息泄漏、禁止不安全配置的负向断言可能是核心契约。
- 删除测试不是删除生产语义的充分依据；生产代码的去留需要单独证明。

## 五、实施与验证

1. 对同一个失效概念一次性收尾：实现、消费者、路由、注册、配置、专属测试/Fixture、文档、依赖和打包声明；不要保留只用于过渡的永久 Adapter。
2. 保留现行契约对应的有效测试。未改变仍支持的行为时，不新增“证明代码已删除”的测试。
3. 使用最小有判别力的现有检查：符号/路径残留搜索、关联单测、类型检查、相关构建或打包验证。涉及入口或发布资源时，构建检查可能比孤立单测更关键。
4. 对于语义清理，若现有测试完全无法验证受影响的有效行为，明确说明验证缺口；不要临时搭建一整套新测试体系，也不要声称已充分验证。
5. 实际检查 diff 和工作区，确保未误删用户修改、未引入新兼容层或意外扩大范围；仅在发现明确问题时追加检查。

**成功标准**：当前有效行为与契约仍成立，且需要维护的实现路径、真相源、接口或支撑概念净减少。不是提高“删除行数分数”，也不是仅仅让所有测试变绿。
